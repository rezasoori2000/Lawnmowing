# TurfOps Mobile App

A React Native (TypeScript) app for logging and tracking turf/lawn mowing for a small NZ
farm/turf operation. This is a **bare React Native CLI** project (not Expo) with a single
shared `src/` codebase that builds to both Android and iOS via the generated `android/` and
`ios/` native project folders.

This README covers Phase 1 / Stage 1 scope: dashboard, lawn areas, logging a mow, mowing
history, and basic reports, plus a simple email/password login. See "Out of scope" at the
bottom for what's intentionally deferred.

## Prerequisites

- **Node** 20.x (already installed)
- **Java** 17 (already installed)
- **Android SDK** at `%LOCALAPPDATA%\Android\Sdk` (already installed), with at least one AVD
  created in Android Studio's Device Manager, or a physical device with USB debugging enabled
- Windows environment variables (check with `echo $ANDROID_HOME` in Git Bash / PowerShell):
  - `ANDROID_HOME=%LOCALAPPDATA%\Android\Sdk`
  - `%ANDROID_HOME%\platform-tools` and `%ANDROID_HOME%\emulator` on `PATH`
- For iOS builds specifically: a Mac with Xcode + CocoaPods (not applicable on this Windows
  dev machine, but the `ios/` project is kept working and buildable there).

## Getting started

```bash
cd mobile
npm install
cp .env.example .env   # adjust API_BASE_URL if needed - see below
```

### Run on Android

1. Start an emulator (or plug in a device with USB debugging on) and confirm it's visible:
   ```bash
   adb devices
   ```
2. Start Metro and build/install the debug app:
   ```bash
   npx react-native run-android
   ```
   (or `npm run android`)

If you only want to confirm the native Android project compiles without a device attached:

```bash
cd android
./gradlew.bat assembleDebug
```

### Run on iOS (on macOS)

```bash
cd ios && pod install && cd ..
npx react-native run-ios
```

## Pointing at the real API

The app talks to the .NET 8 Web API (being built in parallel at `../api`, exposing
`/api/lawn-areas`, `/api/mow-records`, `/api/people`, `/api/equipment`, `/api/reports`) through
a single axios client, `src/api/client.ts`, configured from `src/config/env.ts`.

To point at a real backend:

1. Edit `mobile/.env` (git-ignored; copy from `.env.example`):
   ```
   API_BASE_URL=http://10.0.2.2:5000/api   # 10.0.2.2 = host loopback from the Android emulator
   API_TIMEOUT_MS=15000
   ```
   - From a physical device on the same network, use the machine's LAN IP instead of
     `10.0.2.2`, e.g. `http://192.168.1.50:5000/api`.
2. Restart Metro with `--reset-cache` so the new env values are picked up:
   ```bash
   npx react-native start --reset-cache
   ```

**Nothing else needs to change.** Every resource module under `src/api/` (`lawnAreas.ts`,
`mowRecords.ts`, `people.ts`, `equipment.ts`, `reports.ts`) already calls through `apiClient`
first and only falls back to the local in-memory seed data (`src/api/localRepo.ts`) if the
request fails - so the app is fully usable today (API unreachable) and will start showing real
data the moment the API comes up, with no code changes required.

Auth: `POST /auth/login` is expected to return `{ token, user }`. If that endpoint isn't
reachable yet, `src/api/auth.ts` falls back to a locally-generated dev session so you can still
sign in and exercise the rest of the app.

## Project structure

```
mobile/
  App.tsx                  # entry point: providers + RootNavigator
  .env / .env.example       # API_BASE_URL etc. (see above)
  android/, ios/            # native projects generated by React Native CLI
  src/
    api/                    # axios client, React Query hooks per resource, local fallback data
      client.ts             # shared axios instance (auth header injection, 401 handling)
      queryClient.ts        # React Query QueryClient config
      localRepo.ts          # in-memory seed/fallback data + CRUD used when the API is down
      lawnAreas.ts, mowRecords.ts, people.ts, equipment.ts, reports.ts, auth.ts
    components/             # shared UI: Screen, Card, StatusBadge, PrimaryButton, form fields,
                             # SearchablePickerField (searchable + "add new"), ChipSelectField
    config/
      env.ts                # typed wrapper around react-native-dotenv values
    constants/               # seed lists: people, equipment, lawn area names, frequency/mow options
    navigation/              # React Navigation: AuthNavigator, MainTabNavigator, LawnAreasNavigator,
                             # RootNavigator (auth-gated), typed param lists in types.ts
    screens/
      auth/LoginScreen.tsx
      Dashboard/DashboardScreen.tsx
      LawnAreas/LawnAreasListScreen.tsx, LawnAreaDetailScreen.tsx, AddLawnAreaScreen.tsx
      LogMow/LogMowScreen.tsx
      History/MowHistoryScreen.tsx
      Reports/ReportsScreen.tsx
    store/
      authStore.ts           # zustand store; JWT persisted via react-native-keychain
    theme/                   # colors (incl. due/overdue green/orange/red), spacing, typography
    types/                   # shared domain types mirroring the API DTOs (LawnArea, MowRecord, ...)
    utils/
      date.ts                # ISO date helpers
      dueDate.ts              # core due/overdue calculation - see tests
    validation/               # zod schemas for the Log a Mow and Add Lawn Area forms
```

## Key architectural decisions

- **State/data**: React Query owns all server state (caching, retries, invalidation).
  Auth/session is the only thing in a plain store (Zustand), since it's small and needs to be
  read synchronously by the axios interceptor.
- **Offline-friendly by construction, not by a sync engine**: every query/mutation hook tries
  the real API first and falls back to `localRepo` (in-memory, seeded with realistic demo data)
  on failure. This satisfies "usable before the API exists" without building the real offline
  sync engine that's explicitly out of scope for this phase.
- **Due/overdue logic is 100% client-side date maths** (`src/utils/dueDate.ts`): due date =
  last mowed + frequency.minDays, overdue once past last mowed + frequency.maxDays. No push
  infrastructure is required for Phase 1 - the Dashboard just computes status on read.
- **Forms**: react-hook-form + zod resolvers for both multi-field forms (Log a Mow, Add Lawn
  Area), matching the "schema validator" requirement and giving type-safe form values.
- **Pickers**: lawn area / person / equipment use a custom `SearchablePickerField` (modal +
  search + optional "Add new") rather than a native `<Picker>`, since the spec calls for
  search-as-you-type and inline creation of people/equipment. Mow height / direction / frequency
  use a lighter `ChipSelectField` since those option sets are small and fixed.

## Testing

```bash
npx tsc --noEmit     # strict TypeScript check
npx eslint . --ext .ts,.tsx
npx jest
```

Unit tests currently cover:
- `src/utils/__tests__/dueDate.test.ts` - the due/overdue date-math utility (ok / due-soon / due
  / overdue transitions, custom frequencies, no-history-yet case, urgency sorting).
- `src/validation/__tests__/lawnAreaSchema.test.ts` and
  `src/validation/__tests__/mowRecordSchema.test.ts` - the zod schemas backing the two forms.

## Out of scope for this pass (extension points only)

These are called out in the product spec as later phases; the code has TODO comments / clean
seams where they'd plug in, but nothing is implemented:

- Job timers and machinery service/hours profiles (Phase 2) - see the TODO in
  `src/types/index.ts` on `LawnArea`/`MowRecord`.
- Automatic weather capture - would attach to `MowRecord` alongside job timers.
- Turf/spray/irrigation history (Phase 3).
- Real push notifications for due/overdue - due/overdue is computed client-side on read
  instead; wiring a notification service is a follow-up.
- An offline sync engine (background queue, conflict resolution) - today the app falls back to
  local seed data on API failure, which is enough to develop and demo against but is not a
  durable sync layer.

## Known deviations from the brief

- The generated Android package id is `com.lawnmowingapptmp` (an artifact of the RN CLI init
  process before the project was renamed to TurfOps/LawnMowingApp). Renaming this touches
  `android/app/build.gradle`, `AndroidManifest.xml`, and moves Kotlin source folders - low risk
  to change later, but left as-is for this pass since it's an internal identifier with no user
  visible impact. `app.json`'s `displayName` ("TurfOps") and `package.json`'s `name`
  ("LawnMowingApp") are correct.
- `react-native-vector-icons` was intentionally left out - the bottom tab bar uses plain emoji
  glyphs instead, to avoid the extra native font-linking step for this pass. Swapping in a real
  icon set later is a small, isolated change in `src/navigation/MainTabNavigator.tsx`.
